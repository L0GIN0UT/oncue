# media_pipeline

Генерация ассетов загадок по уровням, хранение в S3, подписанные ссылки, проверка UGC-изображений.

- Пакет: `media_pipeline_service`; запуск: `media_pipeline api|relay|consumer|worker|all|migrate`
- Карточка сервиса (данные, события, деградация): `docs/architecture/services.md`
- Публичный API: нет (только internal: сервисный токен identity, `aud = GV_INTERNAL_AUTH__AUDIENCE` (по умолчанию `media_pipeline`), scope `assets.link`)
- Зависимости: PostgreSQL, Redis (лимит выдачи ссылок), Redpanda, RabbitMQ, S3/MinIO, ffmpeg
- Статус: этап 3a — 9 типов загадок (+ `audio_reverse`, `soundtrack`, `audio_blackout`, `frame_sequence`, `description`, `emoji`), динамические профили (ADR 0025), тексты загадок из catalog (ADR 0024). Этап 3b — свои эмодзи сборников: наборы со `scope` (ADR 0029), `GET /admin/v1/sources`.

## Особенности
- Новый ClueType = генератор в `application/generators` + регистрация в `infrastructure/container.py` + схема `contracts/clues/*`. Генератор сам объявляет исходники (`source_kind`, `source_count`, `sources_for`: лучший, N кадров по `position`, текст с нужными полями); нет исходников — набор не планируется. Use-cases не ветвятся по типу.
- Профили: статические — `config/asset_profiles.yaml` (внутри пакета: образ ставится `--no-editable`), хэши = golden `profile:<clue>:<profile>`; динамические — `asset_profiles_dynamic` по `game.ClueAssetsRequested` (ключ `dyn_<16 hex>`, лимит, досоздание задачей `media.profiles.backfill`). `params_hash` — от params в записанном/присланном виде. Модели `domain/clues.py` = `contracts/clues` + монотонность уровней.
- `api` и `infrastructure` — независимые слои: роутеры получают готовые use-cases, сборка — в `main.py` через `MediaContainer`. Адаптеры создаются без подключений (экспорт OpenAPI без инфраструктуры); нет зависимости → 503 при обращении.
- Задача `media.generate_asset_set` (`task_id = <id>:<generation>`) ставится ДО коммита: в consumer коммит делает `EventProcessor`. Воркер: набора/поколения не видно → исключение и ретрай очереди; устаревшее поколение → no-op.
- Consumer: use-cases работают в SAVEPOINT внутри транзакции inbox (`SqlMediaUnitOfWork(session=...)`). Устаревшие по `version` события отбрасываются.
- Блокировка единицы удаляет объекты ассетов сразу (выданные ссылки перестают работать до TTL); разблокировка — новое поколение генерации.
- Ключи объектов `a/<128 бит hex>.<ext>`; объект без строки в `asset_levels` недоступен (ссылки выдаются только по БД).
- Аудио: `-ss/-t` стоят ДО `-i` (уровень физически не содержит позднего звука); длительность файла = отрывок + 1 AAC-кадр тишины (23 мс).
- `AssetBlockedError` — наследник `gv_core.GoneError`: 410 `asset.blocked` отдаёт общий обработчик `gv_service` (своих Problem/`problem_responses` в сервисе нет).
- Версия `AssetsReady`/`AssetsFailed` монотонна по `media_item_id` (= `aggregate_id`), а не по набору: счётчик `media_items_state.events_version`, инкремент `items.next_event_version` в транзакции записи события в outbox (возможны пропуски). Порядок блокировок: строка единицы → набор (как в consumer).
- Admin-мутации (upload, regenerate): `admin.access` + своё право, `gv_service.IdempotencyKey`, `gv_service.Reason`; ключ и ответ — `gv_db.idempotency.run_idempotent` в транзакции мутации (`uow.idempotency`, таблица `idempotency_keys`). Повтор upload отвечает до перекодирования файла. Чтение `GET /admin/v1/asset-sets` (с `scope`) и `GET /admin/v1/sources` (только каталожные исходники, по виду и `position`, без адресов S3) — `admin.access`.
- Лимит выдачи ссылок в Redis — fail-closed: 503 с `details.retry_after` (`GV_MEDIA__LINK_LIMITER_RETRY_AFTER_S`) → заголовок `Retry-After`. Журнал `link_issuance` хранит только sha256 субъекта (`subject_hash`) и `client_id`, чистит его задача relay `media.link_issuance.purge` порциями.
- Тексты загадок: из `MediaItemCreated/Updated` (одобренные `clue_texts` + год, жанры, страны, персоны, без названия) — один исходник `kind=text` с содержимым в строке БД, id = uuid5(единица, sha256 содержимого): правка → новый исходник → новое поколение. Ассет уровня — JSON `text_asset.v1` (`application/json`, ключ `a/<hex>.json`).
- Свои загадки сборников (ADR 0029): consumer `collections.collection.v1` (`Published/Updated/Deleted`, версия — `collections_state`, удалённый остаётся надгробием) → текстовый исходник `origin=collection` со `scope=(collection, id)` (id = uuid5 владельца, единицы и хэша) → `PlanAssetSets(scope=…)` только по профилям `GV_MEDIA__SCOPED_CLUE_TYPES` (`emoji`, статические и динамические; backfill тоже) → `AssetsReady/Failed.scope`. Каталожный путь (`list_for_item(scope=None)`) scoped-строки не видит; блокировка единицы выключает наборы любого владельца. Эмодзи вне `gv_text.emoji.is_strict_emoji` (лимит `GV_MEDIA__COLLECTION_EMOJI_MAX_GRAPHEMES`) или повтор единицы → `PermanentError` (DLQ); скрытый сборник не проверяется. Эмодзи убрали / `hidden` / `Deleted` → строки наборов и исходников удаляются, объекты — `delete_quietly` после коммита; события об удалении нет (game сверяет по своему снимку сборника). Эмодзи короче профиля (встроенный `emoji` — 6) → набора нет. Задача генерации удалённого набора ретраится до DLQ (`TaskNotVisibleError`) — редкая гонка, принято.
- UGC-изображения (5b, поток S3; ADR 0048, зона повышенной безопасности — загрузка пользовательских файлов): приём `POST /internal/v1/ugc-images` (сервисный токен, scope `ugc.image`; клиент — `sub = svc:<id>`, должен быть в `allowed_clients` назначения из `config/ugc_purposes.yaml`), очередь модерации `/admin/v1/ugc-images` (право `media.ugc.moderate`). Код: `domain/ugc.py`, `application/{commands,queries}/ugc.py`, `infrastructure/ugc_images.py` (Pillow), таблица `ugc_images` (миграция `0008`; в плане была `0003`, но номера заняты).
  - Файл: тело читается с жёстким лимитом `max_bytes` ДО декодирования (413); тип — по сигнатуре/декодированию (jpeg/png/webp), стороны проверяются по заголовку до `load` (защита от «бомб»), ровно 1 кадр (APNG/анимированный WebP/GIF/SVG/ICO — 422 `ugc.invalid_image`, деталей клиенту нет), результат — центр-кроп до квадрата `output_side_px`, WebP без EXIF/ICC. Имя файла и `Content-Type` клиента игнорируются.
  - Хранение: pending в бакете ассетов `p/<128 бит hex>.webp` (ключ только из `secrets`), модератору — поток байт `GET /admin/v1/ugc-images/{id}/preview` (только `pending`, `image/webp`, `no-store`/`nosniff`, чтение из S3 по ключам сервиса, аудит `ugc.preview`; не `pending` — 409 `ugc.not_pending`; ADR 0061), подписанных ссылок на `p/` нет (`NginxSecureLinkSigner` подписывает только `a/`); approve копирует в `u/<новый hex>.webp` (копия — до коммита, при неудаче удаляется), `p/` удаляется после коммита. Удаление объектов гарантировано: ключи (отклонение, снятие, замена, отмена заявки, исходный `p/`) пишутся в `ugc_object_purge` в транзакции решения; после коммита — быстрое удаление, а что не удалось, добивает задача relay `media.ugc.purge` (`UgcObjectPurger.sweep`, до успеха). Осиротевшие `p/` (в S3 есть, строки `pending` нет) старше `GV_MEDIA__UGC_ORPHAN_TTL_H` (24) чистит `media.ugc.orphans`. Gateway: `/ugc/u/<hex>.webp` публично, кэш 1 мин (`max-age=60`). Бакет читается анонимно только по `a/*` и `u/*` (политику перезаписывает job `migrate`; S3 только во внутренней сети, снаружи — gateway); `p/*` анонимно закрыт (ADR 0061).
  - DoS: декодирование — не больше `GV_MEDIA__UGC_ENCODE_CONCURRENCY` (2) файлов одновременно (остальные ждут), JPEG уменьшается декодером (`draft`) до `load`; лимит заявок на игрока — в progression (до вызова media).
  - Идемпотентность: приём — по `(owner_user_id, Idempotency-Key)` (повтор отвечает до кодирования); решения — `(moderator, Idempotency-Key)`. Новая заявка владельца на то же назначение тихо снимает прежнюю `pending` (`rejected/superseded`, событие не публикуется); advisory-lock на `(владелец, назначение)`.
  - Решения: `FOR UPDATE` строки (из двух конкурирующих побеждает одно, второе — 409 `ugc.not_pending`); reject разрешён из `pending` и `approved` («снятие»: version растёт, `u/` удаляется); `AssetModerated` — в outbox той же транзакцией, `version` = число решений (у `pending` в API показывается 1), без `moderator_id` и свободного текста, `reason_code` — из конфига.
  - Замена: одобрение нового ассета под тем же `lock_owner(owner, purpose)` тихо переводит прежние `approved` владельца в `rejected/replaced` (служебный код, не из списка модераторов; version +1, `u/` — в очередь удаления, события нет: `approved` нового B и так заменяет A в progression).
  - Решение модерации social (5c): consumer `social.ContentModerated` (`content_removed`, `target_kind = avatar`, `target_id` = id ассета) → `RemoveModeratedUgcImage` (тот же `reject` из `approved`, код причины — `GV_MEDIA__UGC_SOCIAL_REMOVAL_REASON`, ключ `social-case:<case_id>`; объекты `u/` удаляет задача `media.ugc.purge`, а не обработчик до коммита — `DeferredUgcPurger`); ассета нет или уже отклонён — без изменений.
- Загрузка вне local/ci требует `origin`/`source_url`/`license_note` (D6, `source.provenance_required`).
- Генерация тяжёлая (ffmpeg, Pillow): воркер берёт не больше `GV_TASK_PREFETCH` задач (по умолчанию 2), лимит памяти контейнера — `memory_mb` в `infra/services.toml`.
- Один `MediaContainer` на процесс (`container_for`); его `close` (ленивое соединение RabbitMQ) регистрируется в `Infrastructure.add_closer` — закрывается для любой команды.
- Тестовые фейки портов сервиса — в `tests/conftest.py` (фикстура `media`, хуки сбоев `fail_commit`/`after_commit`), без правки `sys.path`. `load_example` по умолчанию даёт новый `event_id`; `fresh_id=False` — только для проверки дублей.
