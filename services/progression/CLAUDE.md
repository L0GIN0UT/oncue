# progression

Опыт и уровни, валюта (журнал проводок), задания, бейджи, магазин, инвентарь, оформление профиля.

- Пакет: `progression_service`; запуск: `progression api|relay|consumer|worker|all|migrate`
- Карточка сервиса (данные, события, деградация): `docs/architecture/services.md`
- Публичный API: `/api/progression/v1/...` на gateway
- Зависимости: PostgreSQL, Redpanda, Redis (лимит попыток промокода), S3 (картинки предметов), media-pipeline (internal, только загрузка аватарки)
- Статус: этап 5b, поток S1 — магазин и промокоды (`docs/plans/stage-5.md`). Решения: ADR 0042–0048.

## Особенности
- Контракты: события `contracts/events/progression/*` (топик `progression.progression.v1`, ключ — `user_id`), конфиг `contracts/progression/progression_config.v1.json` (опыт, уровни, Версы, задания, бейджи, колесо, лимиты выдачи; значений в коде нет). Часовой пояс суток — поле `timezone` конфига.
- Ledger (зона повышенной безопасности): `xp_ledger`/`currency_ledger` append-only, `UNIQUE(op_id)`, баланс — в той же транзакции, не ниже нуля, сторно — встречная проводка `reversal_of`. После реализации — «требуется ручная проверка владельцем».
- Идемпотентность начислений — по предмету события (`op_id`), не по `event_id`; дейлик награждается только по `DailyCompleted`.
- Admin-API (P3): `application/admin` + `api/admin`; таблицы `admin_actions`, `idempotency_keys` (`tables_admin.py`, миграция `0004`). Выдача/сторно — под блокировкой `progress` игрока (суточный лимит в `config.timezone`, считаются и сторнированные выдачи), `op_id = admin:{Idempotency-Key}`; сторнируется только журнал Версов, не опыт. Счётчики заданий/бейджей — `SqlStats` (нули до P2).
- Права admin-API: `admin.access` + `progression.config.manage|publish`, `progression.ledger.grant|reverse|read` (identity `0013`).
- `SeasonStandingsFinalized` приходит пачками без порядка: идемпотентность по `(season_id, chunk)`, награды по месту из пачки, не ждать другие пачки и `SeasonFinished`.
- `RewardHook.online_xp_multiplier` вызывается под `FOR UPDATE` игроков матча — I/O внутри запрещён; версия конфига выбирается по `finished_at` события (ADR 0042), не по времени обработки.
- consumers - `infrastructure/messaging/__init__.py`, как в rating/match; новые источники P2 - отдельные модули рядом, регистрируются в `build_event_handlers`.
- P2 (задания, бейджи, колесо, бусты; ADR 0044): метрики копятся в `metric_counters`, предмет события отмечается в `metric_marks` (повтор с новым `event_id` метрики не двоит); задания назначаются снимком на период (`quest_assignments` + `quest_progress`), награда — через ledger P1.
- Метрики P2 обновляются в одной транзакции с начислением P1 (`messaging/rewards.py`): ошибка P2 откатывает и P1, событие повторяется; payload разбирает P1, P2 не строже.
- Буст опыта: `BoostRewardHook` тратит матч буста в транзакции матча (только при базовом опыте > 0, `boost_spends` PK `(user_id, match_id)`); Версы и соло бустом не множатся.
- Колесо: `wheel_spins` PK `(user_id, day)`, сектор выбирает порт `Random` (`container.random`), приз выдаётся в той же транзакции; `GET /me/quests` пишет назначение.
- Сид конфига — `seeds/progression/config.yaml`; задача relay `progression.config.bootstrap` (`GV_PROGRESSION__BOOTSTRAP_CONFIG_DIR`, только local/ci) публикует версию 1, если опубликованной нет (актор `UUID(int=0)`); начисления до неё повторяются.
- 5b, S1 (ADR 0045–0049; миграции `0005`, `0006`): магазин, инвентарь, оформление, промокоды, паки — `application/{shop,inventory,appearance,promo}`, `application/admin/shop.py`, `domain/{shop,inventory,appearance,promo,packs}.py`, `api/public/shop.py`, `api/admin/shop.py`. Секции конфига `shop`/`promo`/`spend` необязательны: нет `shop` — магазин пуст.
- Покупка: блокировка `progress` игрока → повтор по `op_id = shop:{user}:{item}` → бакет `earned` `FOR UPDATE` → `CurrencyDebited` + `inventory` + `ItemPurchased` в одной транзакции. Открытие по уровню — лениво (`INSERT … ON CONFLICT DO NOTHING` при чтении витрины/инвентаря и PUT оформления). Колесо: предмет → инвентарь `source=wheel`, дубль → Версы по редкости (`wheel:{user}:{day}:dup`); нет предмета в `items` — ERROR `progression.wheel_item_missing` и запись `grants_log`.
- Промокод: в БД только HMAC-SHA256 (`GV_PROGRESSION__PROMO_HMAC_KEY`; вне local/ci без него падает job `migrate`, а первое хеширование — ошибкой; читается лениво), PK `(code_hash, user_id)`, счётчик под `FOR UPDATE` строки кода, `per_user_once` — один код партии на игрока, `promo_id` события = id кода; лимит попыток (Redis, fail-closed) по игроку и IP из секции `promo`. Суточные потолки эмиссии (`promo.max_daily_verses_per_actor|total`, сутки в `config.timezone`, отозванные партии считаются, порядок `batch <= actor <= total` проверяет домен): проверка и вставка партии под `pg_advisory_xact_lock` суток, 422 `promo_actor|total_daily_cap_exceeded`. Коды партии показываются один раз, повтор ключа — 409 `codes_already_shown`.
- Картинки предметов: Pillow (сигнатура, декод всех кадров, лимиты `shop.media`), объект в бакет `GV_PROGRESSION__COSMETICS_BUCKET` под `c/<32 hex>`, публичный префикс `GV_PROGRESSION__COSMETICS_BASE_URL`; бакет и политика создаются в job `migrate`. Паки: только CRUD; витрина — 404 пока `GV_PROGRESSION__BILLING_ENABLED=false`.
- 5b, S3 — своя аватарка (ADR 0048, миграция `0007`): `application/avatar`, `domain/avatar.py`, `api/public/avatar.py`, `infrastructure/{media_client.py,db/repositories_avatar.py,db/tables_avatar.py}`. Право — предмет `shop.custom_avatar_item_key` в инвентаре (иначе 403 `progression.avatar_not_entitled`; публикация конфига проверяет, что предмет есть, продаётся и лежит в `shop.slots` — 422 `progression.config_invalid`). `POST /v1/me/avatar`: право → один вызов media-pipeline (`GV_PROGRESSION__MEDIA_URL`, токен scope `ugc.image`, `Idempotency-Key` пробрасывается; сеть/5xx/неожиданный ответ → 503 без деталей) → `avatar_requests`; прежняя `pending` закрывается как `superseded`. Тело читается с лимитом `GV_PROGRESSION__AVATAR_MAX_BYTES` (413). Лимит заявок на игрока — `GV_PROGRESSION__AVATAR_SUBMIT_LIMIT` за `AVATAR_SUBMIT_WINDOW_S` (5 в час, Redis, fail-closed 503) до вызова media и после проверки права: превышение — 429 `progression.avatar_rate_limited` + `Retry-After`. `AvatarLimits` в `GET /me/avatar` берутся из настроек progression (`AVATAR_*`) и ДУБЛИРУЮТ `config/ugc_purposes.yaml` media-pipeline (без синхронного вызова на чтение) — менять вместе. Consumer `media_pipeline.AssetModerated` (топик `media_pipeline.ugc_image.v1`, только `purpose=avatar`): версия на `asset_id` хранится в `avatar_requests.version` (`INSERT … ON CONFLICT DO UPDATE WHERE version < excluded`), поэтому дубль и вывод вне порядка дают один эффект и решение, пришедшее раньше заявки, не теряется; `approved` → `user_avatars` (новее по `approved_at` заменяет), `rejected` → снимает аватар, только если он текущий. Публичный адрес — `GV_PROGRESSION__UGC_BASE_URL` + `public_key` (`custom_avatar_url` в `/v1/appearance`, `current_url` в `/me/avatar`; в `me/appearance` поля нет по схеме). Ответы `/me/avatar` — `private, no-store`.
- Сид магазина (5b, `seeds/progression/items/`: `items.yaml`, `packs.yaml`, `images/*.webp` ≤ 50 КБ, генератор `seeds/progression/generate_items.py`). Порядок засева: bootstrap публикует v1 с `shop.custom_avatar_item_key: null` (иначе 422: предмета ещё нет) → `gv dev seed` (шаг `seed_progression`, admin-API, идемпотентно по ключу) создаёт предметы, грузит картинки, активирует, создаёт пак → публикует следующую версию конфига с ключом `custom_avatar`. Призы колеса `item_key` — ключи сидовых предметов (тест `test_seeds.py`).
- 5d, E1 — сезонные события (ADR 0054–0056; миграция `0008`): `domain/events_season.py`, `application/events/{unlock,progress,player,tick}.py`, `application/admin/events.py`, `api/{public,admin}/events.py`, `infrastructure/db/{tables,repositories}_events.py`. Запуск публикуется под `pg_advisory_xact_lock` (пересечение — 409 `event_period_overlap`), на публикации кладётся снимок тела + `body_sha256`; игрок и архив читают снимок. Статус `active/finished` считается по времени, `progression.events.tick` лишь материализует его и шлёт `EventRunStarted/Finished`; `stop` шлёт `Finished(stopped)` сразу.
- Находки: серверные триггеры двигаются из `ProgressTracker.apply` (время события; вне периода запуска не считается), колеса (`wheel_spin_streak`) и оформления (`item_equipped`); метрики `weekly_top_place` и `item_equipped` — `EVENT_ONLY`, заданиям и бейджам конфиг их не разрешает. Награда находки — в той же транзакции под блокировкой `progress`: прогресс, проводки `event:{run}:{find}:{user}`, `FindUnlocked`; при последней находке — предмет `source=event` и отметка `event:{run}:complete:{user}`, `EventCompleted`. Финал открывается после остальных (серверный финал копит прогресс скрыто). Предмет награды — `items.event_key` (без цены и уровня, не на витрине, не с колеса, не по промокоду и не в паке); `reward.item_key` обязан быть активным предметом этого события.
- `collection_played` у находки: необязательный `params.collection_keys` (uuid сборников, только эта метрика) — фильтр уровня находки в `Trigger.accepts` по `MetricUpdate.collection_id`, как `slot`/`item_key`; пусто — любой сборник.
- Claim `ui_spot`: лимит `GV_PROGRESSION__EVENT_CLAIM_LIMIT` (`N/окно_с`, Redis, fail-closed), повтор идемпотентен. «Требуется ручная проверка владельцем» (ledger).
- Нет синхронных вызовов game/match/rating; места сезона — из `rating.SeasonStandingsFinalized`, топ недели — топ-100 (решение владельца).
- Роли Postgres (ADR 0060, миграция `0009`): рантайм ходит ролью `progression_app` (`app_role` в реестре), миграции — владельцем `progression`; на `xp_ledger`/`currency_ledger`/`admin_actions` у рантайма только `SELECT/INSERT`. Новая append-only таблица отзывает `UPDATE/DELETE/TRUNCATE` у `progression_app` в своей миграции. Старый том БД: создать роль вручную. «Требуется ручная проверка владельцем».
- Gateway: `POST /api/progression/v1/me/avatar` — отдельный `location =` в `infra/nginx/nginx.conf` с `client_max_body_size 2m` (аватарка ≤ 1,5 МБ + multipart); страж — `tools/gv/tests/test_gateway_body_limit.py`; 413 nginx отдаёт Problem JSON `request.payload_too_large`.
- Сверка журнала инкрементальная (ADR 0062, миграция `0010`): `reconcile_checkpoints` хранит id последней покрытой проводки (uuid7, граница — «сейчас − `RECONCILE_LAG_S`»), точка двигается после проверки куска; полный проход раз в `RECONCILE_FULL_EVERY_S`. Усечённая выдача куска (`len == limit`) точку не двигает: кусок сужается вдвое (лог `progression.reconcile_chunk_truncated`), пока все расхождения не поместятся. Метрика `gv_progression_ledger_mismatches` держит открытые расхождения полного прохода. Партиционирование журналов отложено до порога (ADR 0062), `UNIQUE(op_id)` не трогать.
- Ретенция (`progression.retention.purge`, `GV_PROGRESSION__RETENTION_*`): только `metric_marks` и `quest_progress` дневных/недельных периодов; журналы и разовые задания не удаляются. «Требуется ручная проверка владельцем» (ledger).
- `collection_played` у находки: необязательный `params.collection_tags` (ключи тегов, ADR 0067) — засчитывается сборник хотя бы с одним тегом, события без `collection_tags` не проходят; вместе с `collection_keys` — «и».
- `PlayerAppearance.custom_avatar_asset_id` (необязательное, ADR 0069): ассет одобренной аватарки — объект жалобы `avatar`.
- `PUT /admin/v1/events/{key}`: необязательный `expected_body_sha256` (хеш, который видел админ) - расхождение 409 `progression.event_definition_changed`; без поля проверки нет (ADR 0069).
- ADR 0071: `GET /admin/v1/items/{id}` (права списка, `no-store`, 404 `progression.item_not_found`); `GET /v1/me/appearance` отдаёт `custom_avatar_url`/`custom_avatar_asset_id` (единый источник, `MyAvatar.current_url` deprecated на один релиз); миграция `0011` — `EXCLUDE USING gist` по занятому периоду опубликованных запусков (`ex_event_runs_no_overlap`, без `btree_gist`; при существующих пересечениях миграция падает до изменений). Проверка под advisory-lock остаётся. «Требуется ручная проверка владельцем» (ledger-зона рядом).
- Награды за сессию (PR-A): `GET /v1/me/rewards?session_id=` — только чтение `xp_ledger`/`currency_ledger` по `(user_id из токена, source_ref = id сессии)` и причинам `solo_round`/`daily`, без проекции и без записи в ledger. Опыт, Версы, уровень до/после (сумма журнала до проводки по кривой действующего конфига), серия дейлика (домен и день из `op_id` `daily:{user}:{domain}:{day}`, только пока `last_day` серии равен дню сессии). Начисление асинхронное: нет проводок (ещё не пришло, потолок съел всё или сессия чужая) — 200 с `settled=false` и нулями, чужие сессии не раскрываются. Миграция `0012`: индексы `(user_id, source_ref)` на обоих журналах (`CONCURRENTLY`, данные не меняются). «Требуется ручная проверка владельцем» (ledger-зона: индексы и чтение).
