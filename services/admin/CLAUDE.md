# admin

Админ-панель на Django 5.2: вход через identity, разделы «Каталог», «Пользователи» (этап 1), «Режимы» и «Наборы дня» (этап 2), ассеты загадок, тексты загадок, переопубликация (этап 3a), «Сборники» (этап 3b), «Матчи» и онлайн-шаблоны режимов (этап 4a), «Рейтинг» (этап 4b), «Прогрессия» (этап 5a), аудит.

- Пакет: `admin_service`; запуск: `admin api|consumer|migrate|all` (D7; `relay`/`worker` нет)
- Django-настройки: `admin_service.django_settings` — строятся из `admin_service.settings.Settings` (env `GV_*`, `GV_ADMIN__*`)
- Решения: ADR 0006, 0013, 0015, 0024, 0025, 0027, 0032, 0034; планы — `docs/plans/stage-1.md` §7 D2, `docs/plans/stage-2.md` §8 (D6, D8), `docs/plans/stage-3a.md` §9, `docs/plans/stage-3b.md` §11 (D14), `docs/plans/stage-4.md` §10. Карточка — `docs/architecture/services.md`
- Публичного API нет, gateway админку не публикует. Метрики — `:9100`
- Зависимости: PostgreSQL (зеркало пользователей, сессии, аудит, inbox), Redpanda (consumer)

## Особенности
- Своих паролей нет: `IdentityAuthBackend` → `POST identity /internal/v1/admin-sessions {login, password, client_ip}`; права — из **проверенного по JWKS** access-токена, не из JSON ответа. Без `admin.access` не пускаем, даже если identity ответил 200.
- Права Django = снимок perms identity (`identity.<perm>`); `is_staff` ⇔ `admin.access`, `is_superuser` ⇔ роль `admin`. Синхронизация — при входе и refresh (`identity_version = max(текущая, из ответа)`) и по `UserRolesChanged`/`UserDeleted` только при большем `version`. Событие зеркало не создаёт.
- Токены identity в `django_session` — только Fernet-шифротекст (`core.session_crypto`: `GV_ADMIN__SESSION_ENC_KEY` или HKDF от `SECRET_KEY`). Refresh — под `SELECT … FOR UPDATE` строки сессии (две вкладки не шлют один refresh дважды). Выход — `POST /internal/v1/admin-sessions/revoke` (ошибка — в лог, выход всё равно).
- `/login/`, `/logout/` — `core.auth_views` поверх `admin.site`: лимит попыток входа по IP (`GV_ADMIN__LOGIN_ATTEMPTS_*`, кэш Django: Redis при `GV_REDIS_URL`, иначе память процесса) — сверх лимита identity.
- Данные сервисов — только через их admin-API (`core.views.fetch/mutate`; ассеты — `media_pipeline GET /admin/v1/asset-sets`); `ServiceModelAdmin`/`ReplicaRouter` — каркас до этапа 5 (D3).
- Мутация = форма с обязательной `reason` и скрытым `idempotency_key` + `AuditEntry` и при успехе, и при отказе. В `after` — только изменённые поля (`audit_fields`), без e-mail. Просмотр пользователей (`users.view`) тоже аудируется (`audit_read`, поиск по e-mail — без адреса). Аудит append-only: ORM — `AppendOnlyError`, БД — триггеры `audit/0001` (UPDATE/DELETE) и `0002` (TRUNCATE).
- Consumer — `core.events.UserEventsProcessor` (транзакция и inbox в Django ORM) поверх `KafkaEventConsumer`: подходит по протоколу `EventProcessorPort`, без `cast`.
- Меню главной — реестр `AppConfig.gv_menu` (`core.menu.MenuEntry`: заголовок, маршрут, право): пункт без права скрыт, но представление всё равно проверяет право (`require_perm`), а сервис — ещё раз.
- «Режимы» (`apps/game_config`, права `config.modes.view|edit|publish`): конфиги хранит game (D8), клиент — `core.game_client.GameAdminClient`. Редактор — YAML/JSON в `textarea`; `config_text` разбирает текст (дубли ключей, ссылки/якоря YAML и даты запрещены, вложенность ограничена), строит diff по каноничному YAML и номер строки по пути ошибки. «Проверить» — `POST validate` без `Idempotency-Key` (`ServiceClient.query`); сохранение — с `base_revision` (409 `game.draft_conflict` → текст остаётся в форме, показывается diff с текущим черновиком). Тело конфига в аудит не пишется — только ревизия/версия. Предел текста — `GV_ADMIN__MODE_CONFIG_MAX_BYTES` (как у game).
- «Наборы дня» (`apps/game_daily`, права `game.daily.view|curate`): календарь за `from..to` (по умолчанию `GV_ADMIN__DAILY_DEFAULT_DAYS` с «сегодня» в `GV_ADMIN__DAILY_TIMEZONE`, не больше `GV_ADMIN__DAILY_RANGE_MAX_DAYS`), замена единицы через поиск в проекции game и перегенерация — только для `scheduled` (перегенерация — и `failed`); `locked` — только чтение, а запоздалая форма получает 409 `game.daily_locked` (сообщение + аудит отказа). Маршруты — конвертеры `modekey`, `isodate` (`core.converters`).
- Этап 3a. Клиенты admin-API — `core.game_client`, `core.media_client`, `core.catalog_client`. «Режимы»: «Запросить ассеты» (`config.modes.publish`, `POST …/asset-requests`, 409 `game.assets_already_available` — сообщение и аудит отказа), предупреждения `assets.profile_missing` с `path`, панель запросов со статусом профиля из media `GET /admin/v1/profiles` (один запрос на `clue_type`, media недоступен — панель без статуса). «Наборы дня»: `period` (`week` — «неделя с»), тема `subject_id`; смена темы — `regenerate` с `subject_id` (аудит `game.change_daily_theme`, прошлая тема в `before`). «Каталог»: тексты загадок (`catalog.edit_aliases`; `plot_raw` только для сверки, пустое поле = `null`, в аудит — ревизия/статус, не тексты), «Переопубликация» (`catalog.import`, подтверждение), исходники `soundtrack`/`audio_clip` с `position` и происхождением (вне local/ci обязательны — как у media) и `PUT /admin/v1/sources/{id}/position` (`media.upload_source`).
- Этап 3b. «Сборники» (`apps/collections`, клиент `core.collections_client`, права `collections.view|curate|unpublish|restrict_author`): список с поиском (`q` — название и ник автора, `status`, `kind`, курсор), карточка с составом и своими эмодзи автора, «Скрыть/Показать» (`unpublish`), «Рекомендуемое» с порядком `rank` 1..1000 (`curate`, только опубликованные), «Ограничить автора» (`restrict_author`; `user_id` берётся из карточки на сервере, не из формы; снять — `DELETE`). Кураторский сборник — YAML-редактор (`collection_text` поверх `config_text`: единица — `media_item_id` строкой или `{media_item_id, custom: {emoji}}`, подписи «название (год)» — комментариями; предел — `GV_ADMIN__COLLECTION_TEXT_MAX_BYTES`): создание — `POST` (сразу публикуется), новая версия — `PUT` с `base_version` (409 `collections.version_conflict` → diff с текущей версией, текст в форме), домен не меняется; ошибки `collections.publish_invalid` (`details.errors[{path, code}]`) и `request.validation_failed` (`loc`) — таблицей с номерами строк (`ServiceError.details/errors`). Аудит — `collections.hide|unhide|set_featured|restrict_author|unrestrict_author|create_curated|update_curated`: только статусы, версии, флаги, не тексты. «Наборы дня»: тема сетки — страница «Сменить тему» (поиск `GET …/mode-configs/{key}/subjects?q=` + выпадающий список, форма уходит в `regenerate`), UUID руками не вводится; 422 `game.subjects_not_supported` — сообщение. «Каталог»: таблица исходников (`media GET /admin/v1/sources?media_item_id=`, видна с `admin.access`) с формой порядка в каждой строке (`media.upload_source`); прошлый `position` — в `before` аудита.
- Этап 4a. «Матчи» (`apps/matches`, клиент `core.match_client`, право `match.manage` — снимок perms identity, отдельной синхронизации не нужно; у moderator только `match.spectate`, раздел скрыт): активные комнаты (`GET /admin/v1/rooms?phase&cursor`, курсор как у сборников), «Завершить…» — страница с обязательной причиной → `POST …/rooms/{code}/abort` с `Idempotency-Key`, 202 = команда принята владельцем (ADR 0034), 404/409 — сообщение и аудит отказа (`match.abort_room`, в `after` — `accepted`, `version`); итог матча (`GET /admin/v1/matches/{id}`, места, раунды со ссылкой на каталог). Просмотры — `audit_read` (`match.view_rooms|view_result`). Код комнаты — конвертер `roomcode`. «Режимы»: подсказки редактора по сводной схеме game (`GET …/mode-configs/schema`, `schema_hints`: `session` — `oneOf` веток с локальными `$ref`, `anyOf [X, null]`, `discriminator.mapping`; текущая ветка — по `session.kind` текста; схема недоступна — без подсказок), заготовка нового режима по схеме ветки (`?session=solo|online` из формы «Новый режим», значения — `default`/`minimum`/первое `enum`), порядок ключей `session` — как в контракте (`config_text._SESSION_ORDER`), имя ветки union в пути ошибки пропускается. Фильтр «Сессия» в списке: `session_kind` строки, если game его отдаёт, иначе один `GET /v1/modes?session=online` — опубликованный не онлайн = соло, неопубликованные и архивные в фильтр не попадают.
- Этап 4b. «Рейтинг» (`apps/rating`, клиент `core.rating_client`, права `rating.ladders.publish` — ladder-ы, `rating.seasons.manage` — сезоны и пересборка; раздел виден с первым, кнопки сезонов скрыты без второго, сервер проверяет оба всегда): список ladder-ов, карточка (версии, тело версии, diff любых двух версий, по умолчанию черновик против действующей), YAML/JSON-редактор (`ladder_text`: отдельного validate у rating нет — проверка по `ladder.v1.json` и инвариантам происходит при «Сохранить», 422 `rating.ladder_invalid` с JSON-Pointer-путями показывается таблицей с номерами строк), публикация, откат, создание сезона, закрытие сезона (страница подтверждения с отметкой), пересборка лидерборда. Аудит `rating.save_ladder_draft|publish_ladder|rollback_ladder|create_season|close_season|rebuild_leaderboard`: версии, статусы, id сезона — без тела конфига. Ключ ladder-а — конвертер `ladderkey`.
- Этап 5a. «Прогрессия» (`apps/progression`, клиент `core.progression_client`, права `progression.config.manage` — раздел, черновик, колесо, задания; `config.publish` — публикация и откат; `ledger.read|grant|reverse` — журнал Версов, выдача, сторно; пункты меню «Прогрессия» и «Версы: журнал и выдача», кнопки скрыты без права, сервис проверяет всегда). Редактор — как у «Рейтинга» (422 `progression.config_invalid`, `details.errors[{path, reason}]` таблицей с номерами строк); откат копирует версию в единственный черновик; предпросмотр шансов колеса считает `apps.progression.wheel` из тела версии (без API). Выдача/сторно — формы с обязательной `reason` и скрытым `idempotency_key` (ledger: повышенная безопасность, лимиты и сумма суток — в сервисе). Аудит `progression.save_draft|publish_config|rollback_config|grant|reverse`: карточка версии/`balance_after`, без тела конфига.
- Этап 5b. «Магазин» (`apps/shop`, права `progression.items.manage` — предметы и паки, `progression.promo.manage` — партии промокодов; пункты меню «Магазин», «Промокоды»): слот/редкость — выбор из `shop.slots|rarities` действующего конфига (недоступен — текст, проверит сервис); GET предмета по id у API нет — запись ищется листанием списка до первой страницы с ней (≤20×100); отказ сервиса при поиске — страница `gv_service_error` (403/503/502), а не 404; конфиг магазина запрашивается только при показе формы, при POST слот/редкость проверяет сервис. Ключ предмета/пака неизменяем (поле disabled, в запрос — из карточки). Картинка: `PUT …/items/{id}/media` (multipart), предел — `shop.media.static|animated_max_bytes`, не выше `GV_ADMIN__SHOP_MEDIA_MAX_BYTES` (проверка до обращения к сервису); `core.uploads.LimitedUploadHandler` (первым в `FILE_UPLOAD_HANDLERS`) обрывает поток сверх предела пути (`RequestDataTooBig` → 400), `FILE_UPLOAD_MAX_MEMORY_SIZE` не меньше этого потолка (`DATA_UPLOAD_MAX_MEMORY_SIZE` остаётся 2 МБ: файлы в него не входят). Паки без витрины (пометка про `billing.enabled=false`).
- Промокоды: коды существуют только в ответе на POST создания партии (страница `no-store` + `Pragma: no-cache`, «Скачать CSV» — `data:`-ссылка из тех же кодов); в сессию, аудит (`audit_after` — метка/число/тип награды), логи и сообщения не попадают. 409 `progression.codes_already_shown`, 422 потолков (`promo_batch_too_large`, `promo_*_daily_cap_exceeded`) — сообщения с `details` limit/used/requested (`service_client._CAP_CODES`).
- «UGC-изображения» (`apps/ugc`, право `media.ugc.moderate`, методы `ugc_*` в `core.media_client`): очередь (`status` по умолчанию `pending`, `purpose`, курсор), карточка ищется в списке статуса (`?status=`), картинка идёт через прокси `GET /ugc/<id>/preview/` (байты из media `GET …/preview` с токеном модератора, заголовки `no-store`/`nosniff`/`inline`, токен браузеру не уходит; только `pending`, у остальных картинки нет; ADR 0061); «Снять с публикации» — тот же `reject` из `approved`; коды причин — из `GET /ugc-images/settings`; после решения (и отказа) — возврат в очередь с сообщением. Аудит `ugc.approve|reject` (`before.status` — из реальной строки очереди), просмотр картинки — `audit_read` `ugc.view_preview` (в прокси).
- «Рассылки» (`apps/notifications`, клиент `core.notifications_client`, право `notifications.broadcast.send`, адрес `GV_ADMIN__SERVICE_URLS__notifications`): `new/` проверяет форму и показывает подтверждение (сервис не вызывается), `send/` ставит рассылку в очередь с ключом формы; `subject` без управляющих символов. Число получателей API до отправки не отдаёт — показывается в списке. Аудит `notifications.broadcast` (тема и длина текста, без тела).
- Этап 5c. «Модерация» (`apps/social`, клиент `core.social_client`, адрес `GV_ADMIN__SERVICE_URLS__social`; пункты меню «Очередь модерации» — `social.moderate`, «Конфиг social» — `social.config.manage`): очередь (фильтры `status`, `target_kind`, `mine`, курсор), карточка кейса (жалобы с текстом и фрагмент содержимого выводятся только экранированными, просмотр — `audit_read` `social.view_case`, страница `no-store`), «Взять» / «Эскалировать» / «Решить» (`dismissed|content_removed|sanctioned`, санкция — вид, срок, причина; в запросе `version` кейса — 409 `social.case_version_conflict` и `case_already_claimed` показываются сообщением и аудируются). Эскалированный кейс решает «старший» (`social.sanctions.account`, у admin); кнопка скрыта у остальных, сервис проверяет всегда. Карточка игрока (`GET /admin/v1/users/{id}/moderation`: счётчики, санкции, кейсы), выдача и снятие санкций (`social.sanctions.manage`; `account` — ещё `social.sanctions.account`; самому себе — отказ social 403 `self_sanction_forbidden`). Конфиг social — как «Прогрессия» (редактор YAML/JSON, 422 `social.config_invalid` с `details.errors[{path, reason}]` таблицей со строками, публикация привязана к номеру и `body_sha256` черновика, откат — копия в черновик). Аудит `social.case_claim|case_escalate|case_resolve|sanction_grant|sanction_revoke|save_draft|publish_config|rollback_config`: статусы, версии, виды санкций — без текстов жалоб и тела конфига.
- Этап 5d. «События» (`apps/events`, клиент `core.progression_client`, права `progression.events.manage` — раздел, определение, карта, создание запуска; `progression.events.publish` — публикация и остановка, кнопки скрыты без права, сервис проверяет всегда; ключ — конвертер `eventkey`): список, карточка (находки, превью точек по `x_pct`/`y_pct` поверх карты, запуски), определение — YAML/JSON-редактор (422 `event_definition_invalid` таблицей со строками, 409 `event_definition_locked` — сообщение), карта — multipart (предел `GV_ADMIN__SHOP_MEDIA_MAX_BYTES`), «Новый запуск» = и перезапуск (период вводится в UTC), публикация — с чекбоксом подтверждения и скрытым `body_sha256` с экрана (409 `event_body_changed`), остановка, статистика запуска (игроки по находкам). Аудит `events.create|update|upload_map|create_run|publish_run|stop_run`: ключ, хеш, статусы и период — без тела определения.
- Сервисный токен для `/internal/v1/admin-sessions*` (D13): `core.service_auth.identity_headers()` добавляется в каждый вызов identity из `core.auth`; источник — `build_token_source()` (`gv_auth.SyncServiceTokenProvider`, `aud=identity`, из `GV_SERVICE_AUTH__*`; без настроек — `None`, вызов без токена и 401 от identity). Отказ получения токена = «identity недоступен», пароль в identity не уходит.
- mypy с `mypy_django_plugin`: модуль настроек для плагина — `admin_service.django_settings_typecheck` (окружение `ci` по умолчанию, иначе импорт настроек требует прод-секретов).
- Health обслуживает первый middleware — до проверки `Host` и IP-allowlist. Allowlist — по `REMOTE_ADDR`; `X-Forwarded-For` — только от `GV_ADMIN__FORWARDED_ALLOW_IPS`. Вне local/ci `GV_ADMIN__IP_ALLOWLIST` обязателен и не пуст (иначе процесс не стартует); частные сети по умолчанию — только local/ci.
- Статика django-admin отдаётся приложением (`/static/`, без collectstatic): общий Dockerfile не меняем. API админка не публикует (контракта в `contracts/openapi/` нет).
- Тесты: conftest сам делает `django.setup()`; БД `test_admin_<хвост uuid7>`, триггер запрета TRUNCATE в ней выключен ради `flush`. Заглушки (`identity`, `catalog`, `media`, `game`, `collections`, `match`; у `game` по умолчанию отвечает `…/mode-configs/schema` контрактом `mode_config.v1.json`) — `stub_service(service=...)` + проверка по контракту и ответа (статусы из контракта, Problem — фикстура `problem`), и запроса админки (JSON-тело, поля multipart, `Idempotency-Key` у admin-мутаций, где контракт объявляет заголовок); `respond_off_contract` — только для тестов на битые данные. Роль модератора — фикстура `moderator_perms`; сервисный токен в тестах — фейковый `TokenSource` через `monkeypatch` `core.service_auth.token_source`.
- Inbox admin остаётся собственным на Django ORM (ADR 0065): при изменении семантики `libs/messaging.Inbox` проверить и `core.events` (общая граница — `EventProcessorPort`).
- «Типы уведомлений» (`apps/notifications`, `type_urls.py`, право `notifications.types.manage`, ADR 0066): список `GET /admin/v1/notification-types` и строка-переключатель (обязательная `reason`, ключ идемпотентности в форме строки) -> `PUT …/{type}`. Аудит `notifications.type_toggle` (тип и новое состояние).
- «Модерация»: win-trading (ADR 0068) — страница `social/win-trading/` (`social.moderate`, фильтры `kind|severity|user_id`, курсор, `audit_read` `social.view_win_trading`) и блок в карточке игрока из `GET /admin/v1/users/{id}/moderation`; только показ, санкций отсюда нет.
- «События»: редактор находок формой (`apps/events/finds_form.py`, шаблон `_finds_form.html`, `static/admin_events/map_picker.js`) - режим по умолчанию (`?mode=yaml` - расширенный YAML/JSON). Поля `f{i}_*` + `h_*`, скрытое `base` (исходное тело) - всё, чего форма не показывает (лишние поля определения/находок/триггера/params), берётся из него и не теряется при переключении режимов (`op=to_yaml|to_form`). Список: `op=add|del:i|up:i|down:i` без обращения к сервису; финальная находка при сборке встаёт последней, номера - по порядку. Проверка формы (`finds_form.validate`) дублирует схему/`events_season` ради подсказок, дрейф перечней ловит unit-тест по `event_definition.v1.json`; 422 progression раскладывается на поля по пути (`server_field`). Клик по превью карты - статический JS без inline-кода (CSP не задана, но inline не используем), формула долей `pct_from_click` в Python и JS одна.
- «События»: формы определения (находки и YAML) несут скрытое `expected_sha` (хеш при открытии) -> `expected_body_sha256`; 409 `progression.event_definition_changed` показывается сообщением «Определение изменили, откройте заново», введённое остаётся в форме (ADR 0069).
- Рассылки: экран подтверждения показывает число получателей из `GET /broadcasts/audience` (чтение; сбой подсчёта отправку не блокирует). Карточка UGC читается `GET /ugc-images/{id}` (`MediaAdminClient.ugc_image`), поиск по страницам очереди убран.
