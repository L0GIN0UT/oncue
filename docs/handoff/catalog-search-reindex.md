# Поиск по автору и область подсказок: применение на стенде

Ветка `feat/catalog-search-person-scope`. Что изменилось: автоподсказка (`GET /v1/autocomplete`)
ищет по названию, алиасам (в них уже оригинальное название и транслит), исполнителю и режиссёру;
в подсказке есть `creator` (исполнитель или режиссёр) и год; параметр `scope_person` ограничивает
подсказки единицами одной персоны из **всего** каталога.

## Параметр `scope_person`

- Значение: UUID персоны каталога (`person_id`, тот же, что в карточке единицы и в событиях
  catalog). Формат строки — канонический UUID, регистр не важен; не UUID — 422.
- Источник на клиенте: необязательное поле раунда game «персона, задающая область»
  (исполнитель сборника или марафона, режиссёр). Фронт передаёт его в `scope_person` как есть.
- В области: поиск только по названию и алиасам (имя автора ничего не находит),
  `subtitle` и `creator` в ответе `null`, чтобы подсказка не выдавала ответ.
- Кэш подсказок различает области (в ключе `p=<uuid>`).

## Что менять в индексе OpenSearch

Новые поля документа: `people` (text, имена исполнителей и режиссёров), `person_ids` (keyword),
`creator` (keyword, не индексируется). Индекс-версия поднята с `v1` до `v2`.

1. **Выкат образа catalog.** Задача `catalog migrate` (`prepare_resources`) добавляет новые поля
   в действующий `catalog_media_v1` через `put_mapping` (для `dynamic: strict` это допустимо).
   После выката новый образ пишет документы с новыми полями в старый индекс без ошибок; поиск
   по автору для ещё не переписанных документов не находит ничего (деградации старого поведения нет).
2. **Пересборка (когда удобно, без простоя):**

   ```bash
   gv dev catalog-reindex              # или внутри контейнера: service-entry reindex
   gv dev catalog-reindex --no-switch  # репетиция: собрать catalog_media_v2, алиас не трогать
   ```

   Что делает команда: создаёт `catalog_media_v2`, читает единицы из БД порциями по `id`
   (по 500), пишет в v2 с `version_type=external` (версия агрегата), делает догоняющий проход,
   проверяет, что документов в v2 не меньше, чем единиц в БД (иначе алиас не переключается),
   атомарно переключает алиас `catalog_media` с v1 на v2 одним запросом, сбрасывает кэш
   подсказок и делает ещё один догоняющий проход. БД не меняется, v1 остаётся.
3. **Размер и время.** Стенд ~20 000 единиц: ~40 bulk-запросов, три прохода, порядка минут.
   Чтение из БД идёт короткими транзакциями, нагрузка небольшая.
4. **Повтор и обрыв.** Команда идемпотентна: уже записанные версии пропускаются (конфликт 409
   считается успехом). После обрыва просто запустить снова.
5. **Проверка.** `GET /v1/autocomplete?q=eminem` и `?q=нолан` возвращают результаты;
   `GET /catalog_media/_count` (внутри сети) равен числу единиц; в логе
   `catalog.reindex_done switched=true`.
6. **Откат.** `gv dev catalog-reindex --rollback` возвращает алиас на предыдущий индекс одним
   запросом. Документы, изменённые после переключения, команда откат догоняет из БД автоматически (проход в v1). Если проход прервался, повторить
   `POST /admin/v1/items/republish` или повторить пересборку после исправления.
7. **Уборка.** Старый v1 удалять только после проверки (`DELETE /catalog_media_v1`).

Без OpenSearch (`GV_CATALOG__OPENSEARCH__URL` пуст) всё работает на запасном поиске pg_trgm,
который теперь тоже ищет по персонам и понимает область; команда reindex в этом случае
сообщает, что переиндексировать нечего (код возврата 2).
