# Взаимодействие сервисов

> Статус: принято (v1). Решения: [ADR 0003](../adr/0003-two-brokers.md), [ADR 0004](../adr/0004-outbox-and-idempotency.md).

## 1. Три канала

| Канал | Технология | Когда используем |
|---|---|---|
| **Синхронный запрос** | REST/JSON (OpenAPI 3.1), внутренний — HTTP/2 | Нужен ответ прямо сейчас: клиентские запросы, подписанная ссылка на ассет, проверка entitlement |
| **Доменное событие** | Redpanda (Kafka API) | «Что-то произошло» и это интересно другим: `MatchFinished`, `UserDeleted`… Много потребителей, нужен replay |
| **Задача (команда)** | RabbitMQ | «Сделай работу»: нарезать ассеты, синхронизировать плейлист, отправить письмо. Один исполнитель, ретраи, DLQ, приоритеты |
| **Realtime клиенту** | Centrifugo (WebSocket, fallback HTTP-stream) | Состояние комнат, уведомления, ленты |

**Почему два брокера.** События должны храниться и переигрываться: новый потребитель (рекомендации, аналитика) читает историю с начала, а упавший потребитель догоняет с последнего offset. Это модель лога (Kafka/Redpanda). Задачам нужны per-message ack, отложенные ретраи, DLQ и приоритеты — это модель очереди (RabbitMQ). Если сделать всё на одном брокере, одна из моделей превращается в костыль.

**Почему Redpanda, а не Kafka:** Kafka API без JVM и ZooKeeper, один бинарь, меньше RAM на VPS. Клиенты стандартные (`aiokafka`/`confluent-kafka`), так что при необходимости можно перейти на Kafka без изменений кода.

## 2. Правила синхронных вызовов

1. Таймаут на каждом вызове (по умолчанию 2 с для internal, задаётся в конфиге клиента).
2. Ретраи только для идемпотентных операций: экспоненциальный backoff + jitter, максимум 3 попытки.
3. Circuit breaker на каждую зависимость.
4. Сервисный клиент генерируется из OpenAPI (`contracts/openapi/<service>.json`), а не пишется руками.
5. Цепочки «A → B → C» синхронно запрещены. Если B нужны данные C, B держит проекцию.

## 3. Доменные события

### 3.1. Конверт (envelope)

```json
{
  "event_id": "uuid-v7",
  "event_type": "match.MatchFinished",
  "event_version": 1,
  "occurred_at": "2026-10-07T12:00:00Z",
  "producer": "match",
  "aggregate_id": "room:6GJ4PMRS",
  "correlation_id": "uuid",
  "causation_id": "uuid",
  "payload": { }
}
```

- **Топик:** `<service>.<aggregate>.v<major>`, например `match.match.v1`.
- **Ключ партиции:** `aggregate_id`, чтобы сохранить порядок событий одного агрегата.
- **Схемы:** JSON Schema в `contracts/events/<service>/<EventType>.v<N>.json`. CI проверяет обратную совместимость (раздел 3.4).

### 3.2. Transactional outbox (продюсер)

```
BEGIN
  UPDATE/INSERT доменных таблиц
  INSERT INTO outbox(event_id, topic, key, payload, created_at)
COMMIT
relay (фоновый процесс сервиса) → читает outbox → publish в Redpanda → помечает sent
```

Так событие и изменение данных либо записываются вместе, либо не записываются вовсе. Это гарантия at-least-once без 2PC. Реализация общая: `libs/messaging/outbox`.

### 3.3. Inbox (потребитель)

```
получили событие → BEGIN
  INSERT INTO inbox(event_id) ON CONFLICT DO NOTHING → если 0 строк: дубликат, ack и выход
  обработка (изменения в своих таблицах + свои события в outbox)
COMMIT → commit offset
```

Обработчик идемпотентен по `event_id`. Ошибки: 3 ретрая в процессе, затем событие уходит в топик `<consumer>.dlq` с алертом. Партиция не блокируется.

### 3.4. Эволюция контрактов

- **Можно без новой версии:** добавить опциональное поле.
- **Нельзя без новой версии:** удалить или переименовать поле, изменить тип, сделать поле обязательным.
- Новая major-версия публикуется **параллельно** со старой, пока все потребители не перейдут. Затем старая выключается.
- Потребители игнорируют неизвестные поля (tolerant reader).
- CI-шаг `contracts-check` сравнивает схемы с `main` и блокирует ломающие изменения без новой версии.

## 4. Задачи (RabbitMQ)

- Exchange на сервис-исполнитель, очередь на тип задачи, **quorum queues**.
- Сообщение: `task_id`, `type`, `payload`, `attempt`, `correlation_id`.
- Ретраи — через delay-очереди с растущим TTL (1 с, 10 с, 1 мин, 10 мин), затем DLQ.
- Исполнитель идемпотентен по `task_id`.
- Воркеры — отдельные процессы того же сервиса (`<service>-worker`) и масштабируются отдельно от API.

## 5. Саги (длинные бизнес-процессы)

Распределённых транзакций нет. Многошаговые процессы — это **оркестрируемые саги** с компенсациями. Состояние саги хранится у оркестратора.

| Сага | Оркестратор | Шаги | Компенсация |
|---|---|---|---|
| Слияние аккаунтов | identity | identity merge → каждый сервис переносит данные по `AccountsMerged` и отвечает `MergeStepCompleted` | Переносы идемпотентны. Сага доводится до конца, отката нет (по продукту необратимо) |
| Оплата подписки | payments | платёж → `PaymentSucceeded` → `EntitlementGranted` → progression начисляет бонусы | Возврат → `EntitlementRevoked` |
| Удаление аккаунта | identity | `UserDeleted` → каждый сервис анонимизирует или удаляет свои данные → подтверждение | Повторная публикация до получения всех подтверждений |
| Экспорт в провайдера | library | `ShelfExportRequested` → integrations выполняет → `SyncCompleted` / `SyncFailed` | Статус синхронизации в library и повтор по кнопке |

## 6. Realtime (Centrifugo)

Решение — [ADR 0035](../adr/0035-realtime-centrifugo-tokens-and-tick.md); конфиг — `infra/centrifugo/config.json`; формат сообщения — `contracts/realtime/room.message.v1.json`.

- Публикует **только бэкенд**: match вызывает серверный API Centrifugo (`GV_REALTIME__API_URL`/`API_KEY`). Клиенты не публикуют (`allow_publish_for_client: false`), анонимов нет.
- **Токены с разными секретами:** connection-токен выдаёт identity (`POST /v1/realtime/token`, TTL ≤ 10 мин, без прав на каналы); subscription-токен канала комнаты — match (`POST /v1/rooms/{code}/realtime-token`, только участник). Компрометация match не позволяет подделать вход. Отзыв сессии не рвёт открытое соединение — оно живёт до `exp` connection-токена.
- Каналы: `room:{code}` (4a, история 100 сообщений / 600 с, recovery), `personal:#{userId}` (namespace заведён, потребители — этап 5), `feed:{name}` (публичные ленты, позже).
- Сообщение в канал — **уведомление об изменении с версией** (`version`, `kind`, `delta`). Личное (свои попытки) и скрытое (план, ключи ответа) в канал не идут. При пропуске версии клиент делает REST-ресинк `GET /v1/rooms/{code}/state`, поэтому потеря сообщения не ломает состояние.
- **Фолбэк без WebSocket:** gateway проксирует `/connection/` (WS), `/connection/http_stream` и `/connection/emulation`; при остановленном Centrifugo клиент шлёт `POST /v1/rooms/{code}/tick` (heartbeat присутствия + снимок), матч доигрывается.
- **Синхронный вызов match → game** — единственный на старте матча (план раундов, [ADR 0033](../adr/0033-match-round-plan-from-game.md)); дальше матч не зависит от game. Сбой — отказ старта, комната остаётся в лобби. Не нарушает правило «без цепочек»: game сам в match не ходит.
- Масштабирование: несколько нод Centrifugo с Redis-брокером; `user_connection_limit` действует на узел (учесть на этапе 7).

## 7. Сквозные заголовки

| Заголовок | Назначение |
|---|---|
| `X-Request-Id` | Корреляция. Генерирует gateway, проходит через все вызовы и события (`correlation_id`) |
| `traceparent` | W3C trace context (OpenTelemetry) |
| `Idempotency-Key` | Для всех небезопасных клиентских мутаций |
| `Authorization` | `Bearer <access JWT>` |
