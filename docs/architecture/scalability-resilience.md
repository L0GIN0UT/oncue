# Масштабирование, отказоустойчивость, производительность

> Статус: принято (v1).

## 1. Масштабирование по типам сервисов

| Тип | Сервисы | Стратегия | Метрика автоскейла (k8s) |
|---|---|---|---|
| Stateless API | gateway, bff-web, identity, catalog, game, collections, library, social, progression, payments, notifications | Горизонтально, N реплик за балансировщиком | CPU, RPS, p95 latency |
| Воркеры | media-pipeline-worker, integrations-worker, notifications-worker | По длине очереди | Глубина очереди RabbitMQ (KEDA) |
| Потребители событий | consumer-процессы всех сервисов | Число реплик ≤ числа партиций топика | Consumer lag (KEDA) |
| Stateful realtime | match | Шардирование комнат (single-writer, lease) | Число активных комнат на инстанс |
| Realtime-доставка | Centrifugo | Горизонтально, брокер Redis | Число соединений |

Каждый сервис запускается как **отдельные процессы одного образа**: `api`, `consumer`, `worker`, `relay` (outbox). Они масштабируются независимо.

## 2. Match: модель комнаты

Решение — [ADR 0034](../adr/0034-rooms-process-lease-snapshots.md); реализация — `services/match/CLAUDE.md`.

- **Процесс `rooms`** (отдельный runner образа match; в compose входит в `all`, в Kubernetes — свой Deployment) владеет комнатами. `api` stateless и масштабируется независимо. Лимит — `GV_MATCH__MAX_ROOMS_PER_INSTANCE`.
- У комнаты ровно **один владелец**. Lease `{room:CODE}:owner = instance|epoch` в Redis, TTL 10 с (`GV_MATCH__LEASE_TTL_S`), продление каждые 3 с; захват увеличивает `epoch` (fencing).
- Команды игроков приходят на любой `api` и кладутся в Redis Stream комнаты; владелец применяет их строго по очереди и отвечает через список ответа (≤ `GV_MATCH__REPLY_TIMEOUT_MS`, иначе клиенту 202). Распределённые блокировки на ход не нужны.
- Таймеры фаз — у владельца. После каждого перехода снимок (с `version` и курсором потока) пишется Lua-CAS «owner и epoch — мои»: «зомби» после паузы процесса получает отказ и бросает комнату.
- Падение владельца: lease истекает, другой инстанс (по `orphan_scan_s`) захватывает комнату, читает снимок, не подтверждённые снимком команды применяет заново, таймер пересчитывается по `phase_ends_at`. Разрыв для игроков ≤ lease TTL.
- Плановый деплой: SIGTERM → `stop` (`GV_RUNNERS__STOP_TIMEOUT_S`) → handoff (`GV_RUNNERS__HANDOFF_TIMEOUT_S`): снимок, `DEL owner`, сигнал в `rooms:orphans`. Сумма таймаутов меньше `shutdown_timeout_s` и `stop_grace_period`.
- Итог матча пишется в Postgres вместе с outbox после успешного снимка; пока итог не записан, закрытая комната не отпускается. Повтор после handoff — no-op.
- Известный предел: блокирующий `XREAD` на комнату — ~300 соединений Redis на инстанс; нагрузка этапа 7 ([roadmap](../09-roadmap.md)).

## 3. Горячие точки

| Точка | Риск | Решение |
|---|---|---|
| Дейлик в 00:00 МСК | Всплеск старта игр | Набор дня и ассеты генерируются заранее (за 1 ч), CDN прогревается, статус дня берётся из Redis |
| Лидерборды | Частое чтение | Redis ZSET, ранг за O(log N), страницы кэшируются на 10 с |
| Автокомплит | RPS при каждом нажатии | Debounce на клиенте, кэш популярных префиксов, OpenSearch |
| Ассеты | Трафик | Только CDN. Бэкенд выдаёт лишь подписанную ссылку |
| Матчмейкинг | Пиковые очереди | Пулы в Redis (sorted set по рейтингу), батчевый матчер раз в 1 с, диапазон Эло расширяется со временем ожидания |
| Финиш матча | Каскад событий | Асинхронно: match сразу показывает итоги, Эло и награды приходят событиями через секунды |

## 4. Отказоустойчивость

### 4.1. Механизмы

- **Таймауты** на всех исходящих вызовах (HTTP, БД, Redis, брокеры).
- **Ретраи** с экспоненциальным backoff и jitter — только для идемпотентных операций.
- **Circuit breaker** на каждую внешнюю и межсервисную зависимость.
- **Bulkhead:** отдельные пулы соединений и лимиты конкурентности на каждую зависимость. Медленный провайдер не съедает весь пул.
- **Rate limiting** на gateway и на исходящих вызовах к провайдерам.
- **Health-пробы:** `live` (процесс жив) и `ready` (зависимости доступны, миграции применены). Не готовый под не получает трафик.
- **Graceful shutdown:** перестать принимать запросы, дообработать текущие, закоммитить offset, отпустить lease.
- **Load shedding:** при перегрузке gateway отдаёт 503 с `Retry-After`, а не копит очередь.

### 4.2. Деградация по сервисам

| Упал | Что работает | Что не работает |
|---|---|---|
| identity | Уже вошедшие играют (JWT валиден до истечения) | Новый вход, обновление токена |
| catalog | Игра (проекции), сохранение | Поиск по каталогу, новые импорты |
| media-pipeline | Игра на уже сгенерированных ассетах | Новый контент |
| game | Идущие онлайн-матчи (план раундов уже в снимке комнаты, [ADR 0033](../adr/0033-match-round-plan-from-game.md)), профиль, медиатека | Соло-режимы; старт новых онлайн-матчей («онлайн временно недоступен») |
| match | Соло | Онлайн |
| rating | Матчи (пересчёт догонит) | Свежие лидерборды |
| collections | Игра по уже загруженным в проекцию сборникам | Редактирование и каталог сборников |
| library | Игра | Сохранение (клиент держит локальную очередь и повторит) |
| integrations | Всё, медиатека локально | Синхронизация с внешними сервисами |
| progression | Игра (опыт и валюта начислятся по событиям позже) | Магазин |
| payments | Всё (entitlements из кэша) | Новые покупки |
| social | Игра | Друзья, комментарии |
| notifications | Всё | Уведомления (догонят) |
| Centrifugo | Матчи через HTTP-tick | Мгновенные обновления |
| Redpanda | Синхронные сценарии. Outbox копит события | Межсервисные реакции (догонят) |
| Redis | — (критично) | Сессии игр, комнаты. **Нужна HA: Sentinel** |
| Postgres сервиса | Остальные сервисы | Этот сервис. **Нужна реплика + автофейловер (Patroni)** |

|---|---|

| Доступность онлайн-матчей | 99,5 % / мес |

## 5. Производительность: правила

1. Async-стек целиком (FastAPI + asyncpg + redis-py async). Никаких синхронных вызовов в event loop. CPU-задачи — в воркеры.
2. PgBouncer (transaction pooling) перед Postgres.
3. Никаких N+1: репозиторий возвращает агрегат целиком, для списков — специализированные read-модели.
4. Пагинация только курсорная.
5. Тяжёлые выборки для экранов — из проекций и read-моделей, а не JOIN-ами по ходу запроса.
6. Сериализация через Pydantic v2 (orjson).
7. Сжатие ответов (gzip/br) на gateway, HTTP/2.
8. Ассеты: предгенерация, иммутабельные имена (hash), длинный cache-control на CDN.
9. Нагрузочные тесты (k6) для ключевых сценариев входят в pre-release чек-лист ([../04-testing.md](../04-testing.md)).
