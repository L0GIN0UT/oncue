# 0001. Микросервисы по bounded contexts

- **Статус:** принято
- **Дата:** 2026-10-07

## Контекст
Нужна система, которая масштабируется по узким местам (realtime-матчи, генерация ассетов, чтение каталога), изолирует сбои (внешние API, платежи) и расширяется новыми доменами.

## Решение
13 доменных сервисов (identity, catalog, media-pipeline, game, match, rating, collections, library, integrations, progression, payments, social, notifications) + edge (gateway, bff-web) + admin. Границы — по bounded contexts, критерии выделения — в `architecture/services.md`. Деплой всех сервисов сразу (ещё не реализованные — заглушки), разработка поэтапная.

## Альтернативы
- **Монолит:** проще на старте, но нет независимого масштабирования match и media-pipeline, сбой внешнего провайдера или тяжёлая нарезка влияют на всю систему.
- **Модульный монолит с выделением позже:** рассматривался как стартовый вариант. Отклонён по решению владельца продукта в пользу финальной топологии с первого дня.
- **Более мелкое дробление (сервис на сущность):** приводит к распределённому монолиту и синхронным цепочкам.

## Последствия
- (+) Независимое масштабирование, изоляция отказов, независимый деплой.
- (−) Операционная сложность с первого дня: 16 деплоев, брокеры, наблюдаемость. Компенсируется шаблоном сервиса, общими `libs/` и `gv`-CLI.
- Обязательно: database per service, async-взаимодействие, контракты.
