# 0063. match: общий читатель команд комнат, фоновый отзыв Centrifugo, алерты

- **Статус:** черновик
- **Дата:** 2026-10-25
- **Уточняет:** [0034](0034-rooms-process-lease-snapshots.md), [0052](0052-sanctions-and-enforcement.md), [0059](0059-realtime-disconnect.md)

## Контекст
Хвосты этапа 4a: (1) каждый `RoomActor` держал своё блокирующее `XREAD` потока `{room:CODE}:cmd` - ~300 соединений Redis на инстанс `rooms`; (2) лобби, где никого нет онлайн, закрывалось только общим простоем `room_idle_close_min` (30 мин); (3) повторы `unsubscribe`/`disconnect` с паузой шли в цикле владельца и тормозили комнату при недоступном Centrifugo; (4) не было метрики лага проекции санкций и алертов на сбои отзыва.

## Решение

### 1. Один читатель на инстанс (`infrastructure/rooms/reader.py`)
- `SharedCommandReader` держит один блокирующий `XREAD` сразу по ключам всех комнат инстанса (`count = batch` на поток, `block = GV_MATCH__ROOMS_POLL_MS`). Записи раздаются в «ящики» комнат (FIFO в памяти); актёр ждёт свой ящик (`asyncio.Event`) не дольше дедлайна фазы, как раньше ждал `XREAD`.
- Курсоры в памяти: `consumed` (выдан актёру) и `fetched` (прочитан из Redis). Исходный курсор - из снимка комнаты (подтверждение команд не меняется: `XDEL` и ответы после снимка).
- **Смена набора потоков** (комната появилась/ушла) отменяет текущий вызов и собирает новый. Потерь нет: `XREAD` не удаляет записи, `fetched` двигается только после разбора ответа, ответ отменённого вызова будет прочитан заново с прежних курсоров.
- **Порядок**: поток комнаты читается строго после `fetched`, ящик - FIFO.
- **Откат курсора**: после сбоя итерации актёр перечитывает снимок и приходит с более ранним курсором, чем ожидает ящик - ящик очищается и читается заново с переданного курсора (команды без снимка применяются заново, как в 0034). Ответ вызова, шедшего с прежним курсором, отбрасывается.
- **Закрытие**: `RoomsRunner` запускает читатель задачей и отменяет её после выхода актёров (SIGTERM: актёры выходят на границе итерации, команды остаются в потоке, handoff без изменений). Актёр при выходе вызывает `detach(code)`.
- **Рестарт**: состояние читателя - только память. Новый процесс читает с курсора снимка комнаты; непримененные и применённые без снимка команды остаются в потоке и применяются заново (идемпотентно по `op_id`).
- **Сбой Redis**: читатель логирует `match.command_reader_failed`, считает `gv_match_command_reader_errors_total`, ждёт `rooms_poll_ms` и повторяет; актёры просто получают пустые чтения (запись снимка и lease упадут и без него).
- Соединений к Redis на чтение команд - одно, независимо от числа комнат (метрики `gv_match_command_reader_streams`, `gv_match_command_reader_recompose_total`).
- **Redis Cluster**: ключи `{room:CODE}` лежат в разных слотах, многоключевой `XREAD` в кластере невозможен (`CROSSSLOT`). Сейчас Redis одиночный (compose/k8s); при переходе на кластер читатель делится по слотам (по одному вызову на слот).

### 2. Пустое лобби - локальный таймер владельца
`GV_MATCH__EMPTY_LOBBY_CLOSE_S` (по умолчанию 120, 0 - выключено; не меньше `PRESENCE_TIMEOUT_S`). В `tick` владельца: фаза `lobby`, ни у одного не вышедшего игрока нет heartbeat (`max(seen, joined_at)`) дольше срока - комната закрывается с `reason = empty_timeout`. Решение принимает только владелец по своим часам и heartbeat в Redis. Шина в нём не участвует: у лобби нет событий Redpanda (`MatchStarted`/`MatchFinished` пишутся лишь для сыгранного матча - в Postgres и outbox, при недоступном Postgres закрытие не задерживается), дельта `closed` уходит в Centrifugo после снимка и теряется только как push - клиент ресинкается по `GET /state`. Закрытие лежит в снимке, поэтому не теряется.

### 3. Фоновый отзыв Centrifugo (`infrastructure/revocation.py`)
`RevocationQueue` оборачивает `CentrifugoPublisher` в порту `Subscriptions`: `unsubscribe`/`disconnect` кладут задание в `asyncio.Queue` процесса и возвращаются сразу; `GV_MATCH__REVOCATION_WORKERS` воркеров (стартуют лениво) выполняют отзыв с повторами адаптера. Ёмкость - `GV_MATCH__REVOCATION_QUEUE_SIZE`; переполнение не блокирует команду: лог `match.revocation_dropped` и `gv_match_revocation_dropped_total{kind}`. Остановка (closer инфраструктуры, до закрытия HTTP-клиента): ждём очередь до `GV_MATCH__REVOCATION_DRAIN_S`, остаток сбрасывается с метрикой. Компромисс: потерянный отзыв (переполнение, сброс) остаётся с рисками 0059 - подписка живёт до TTL токена, новый токен не выдаётся; компенсация - алерт `MatchRevocationDropped`.

### 4. Наблюдаемость
- Лаг проекции санкций = `now - envelope.occurred_at` в обработчике `social.UserSanctionsChanged`: гистограмма `gv_match_sanctions_projection_lag_seconds` и gauge `..._last_lag_seconds`. Offset-лаг через admin-клиент Kafka не взят: нужна зависимость и доступ к брокеру из сервиса. Ограничение: зависший consumer без новых событий этой метрикой не виден (нужен экспортёр lag консьюмер-группы - общий алерт «lag > N» из `docs/07-infrastructure.md` §6).
- Правила Prometheus - `infra/observability/prometheus/rules/match.yml` (подключены `rule_files` в `prometheus.yml`): `MatchSanctionsProjectionLag` (N = 60 с), `MatchDisconnectFailed`, `MatchUnsubscribeFailed`, `MatchRevocationDropped` (рост за 10 мин). Runbook - `docs/07-infrastructure.md` §6.1.

## Последствия
- Задержка команды в новой комнате не растёт: появление комнаты пересобирает вызов сразу (событие), а не по таймеру.
- Пересборка набора отменяет вызов и переподключает соединение - цена на создание/закрытие комнаты; при штатной нагрузке (единицы в секунду) пренебрежимо.
- Новые настройки: `GV_MATCH__EMPTY_LOBBY_CLOSE_S`, `REVOCATION_WORKERS`, `REVOCATION_QUEUE_SIZE`, `REVOCATION_DRAIN_S`.
- Зона повышенной безопасности (realtime, санкции): требуется ручная проверка владельцем.

## Дополнение (security-ревью)
- **Бан-отзыв мимо очереди.** `account_banned` отзывается синхронно (`DirectRevoker`), очередь остаётся только для кика/выхода; подробности - [0059](0059-realtime-disconnect.md). Тесты: «очередь полна» и «очередь закрыта» не влияют на бан-отзыв.
- **Надзор за читателем команд.** Раньше неожиданное исключение (не Redis) в `SharedCommandReader.run` молча останавливало чтение всех комнат инстанса. Теперь любой сбой цикла - ERROR `match.command_reader_crashed`, `gv_match_command_reader_errors_total` и повтор с растущей паузой (от `poll_ms` до `GV_MATCH__COMMAND_READER_BACKOFF_MAX_S`, по умолчанию 5 с); `RoomsRunner._supervised_reader` - второй рубеж на случай выхода из `run`. Выбран перезапуск, а не остановка процесса: курсоры и ящики живут в памяти читателя, `XREAD` ничего не удаляет, поэтому команды не теряются, а комнаты не передаются другим владельцам зря. Алерт `MatchCommandReaderErrors` (рост за 5 мин).
