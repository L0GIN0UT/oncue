# 0060. Рантайм-роль Postgres для сервисов с журналами

- **Статус:** черновик
- **Дата:** 2026-10-25
- **Уточняет:** хвост этапа 5 (разделение ролей Postgres для журналов progression)

## Контекст
Журналы progression (`xp_ledger`, `currency_ledger`, `admin_actions`) защищены триггерами append-only, но роль сервиса владела таблицами и могла отключить триггер (`ALTER TABLE … DISABLE TRIGGER`) или выполнить DDL. Компрометация progression открывала правку денег.

## Решение
- Опция реестра `app_role = true` (`infra/services.toml`): у сервиса две роли. **Владелец схемы** `<имя>` выполняет миграции (job `migrate`), **рантайм-роль** `<имя>_app` — api/relay/consumer (`GV_DATABASE_URL` в compose выбирается `gv gen`).
- Рантайм-роль создаёт скрипт инициализации Postgres (пароль `PG_PASSWORD_<ИМЯ>_APP`), права на таблицы выдаёт миграция сервиса (progression `0009`): `SELECT/INSERT/UPDATE/DELETE` на таблицы и последовательности, `ALTER DEFAULT PRIVILEGES` на будущее; на журналах `UPDATE/DELETE/TRUNCATE` отозваны, `alembic_version` недоступна. Рантайм-роль не владелец, поэтому не может отключить триггер, изменить схему или права.
- Ручная выдача и сторно — вставки (сторно — встречная проводка), поэтому отдельной «привилегированной» роли не нужно: сверка читает, выдача вставляет.
- Выдачу прав повторяет job `migrate` при каждом запуске (`GV_PROGRESSION__RUNTIME_ROLE`, `infrastructure/db/runtime_role.py`): роли нет — migrate падает с понятной ошибкой (молчаливый пропуск толкал бы к `GRANT ALL`). Журналы определяются по триггеру `progression_ledger_forbid_mutation`, поэтому новый append-only журнал закрывается автоматически (тест-страж).
- Миграция `0009` без роли ничего не делает (локальная БД одной ролью, тесты). Новая append-only таблица в сервисе с `app_role` обязана отзывать лишние права в своей миграции.

## Последствия
- **Существующие тома БД** не получат роль из скрипта инициализации (он идёт один раз на пустой том): локально — `gv dev db-roles` (идемпотентно создаёт роль из `PG_PASSWORD_PROGRESSION_APP`), затем `gv dev up services`; на сервере — оператор создаёт `progression_app` (`CREATE ROLE … LOGIN`, `GRANT CONNECT`) и перезапускает `migrate`. В Kubernetes — тот же порядок: роль создаёт платформа, миграции идут владельцем.
- Суперпользователь и владелец остаются возможностью обхода: защита рассчитана на компрометацию рантайма, не БД-администратора.
- Расширение на identity (`user_sanctions`, сессии) и ledger других сервисов — флагом `app_role` и миграцией прав.
