# 0034. Процесс `rooms`: команды через Redis Stream, lease с fencing-эпохой, снимки, handoff, итог в Postgres

- **Статус:** принято (план этапа 4; реализовано в 4a, 2026-10-22)
- **Дата:** 2026-10-22
- **Уточняет:** [0010](0010-match-room-single-writer.md)

## Контекст
[0010](0010-match-room-single-writer.md) закрепил одного писателя на комнату. Не решено, где
живёт владелец, как до него доходят команды, что делать с «зомби» после паузы процесса и как
пережить деплой посреди матча.

## Решение
- **Отдельный процесс `rooms`.** `ServiceDefinition.build_runners` (`gv_service.runners`):
  долгоживущие `Runner`-ы с `run(stop)` и `handoff()`. Команда процесса `rooms`; `all`
  запускает их вместе с остальными (VPS, compose); в Kubernetes — свой Deployment. По
  SIGTERM: общий `stop` → ожидание `run` ≤ `GV_RUNNERS__STOP_TIMEOUT_S` → `handoff` всех
  ≤ `GV_RUNNERS__HANDOFF_TIMEOUT_S` → закрытие инфраструктуры. Падение runner-а останавливает
  процесс с ненулевым кодом (честный перезапуск лучше полуживого процесса).
- **Команды.** `api` stateless: кладёт команду в Redis Stream `{room:CODE}:cmd`, ждёт ответ
  `BLPOP {room:CODE}:reply:{op_id}` ≤ `GV_MATCH__REPLY_TIMEOUT_MS`, иначе 202
  `{accepted, version}`. Команда удаляется из стрима (`XACK`) только после снимка.
- **Lease с fencing-эпохой:** `{room:CODE}:owner = {instance, epoch}`, TTL 10 с, продление
  3 с, захват увеличивает `epoch`. Снимок пишется Lua-CAS «owner и epoch — мои»; зомби
  получает отказ и бросает комнату. Hash-tag `{room:CODE}` — готовность к Redis Cluster.
- **Снимок** (`schema_version`, `version`, фаза, `phase_ends_at`, план, игроки, окно `op_id`)
  — после каждого перехода; новый инстанс читает снимок предыдущей версии. Таймеры после
  захвата пересчитываются по `phase_ends_at`.
- **Handoff:** перестать брать комнаты → снимок → `DEL owner` → сигнал в `rooms:orphans`,
  другой инстанс подхватывает.
- **Итог** — Postgres в одной транзакции с outbox: `matches` (`UNIQUE(match_id)`),
  `match_players`, `match_rounds` (партиции по месяцу) и `match.MatchFinished`. Повтор
  записи после handoff — no-op. Redis — горячее состояние, Postgres — история.

## Последствия
- Деплой API не рвёт матчи; деплой `rooms` даёт разрыв не больше lease TTL.
- Порядок ходов в одну миллисекунду детерминирован порядком в стриме.
- Нужны integration-тесты на реальном Redis: два runner-а, kill одного, зомби с устаревшей
  эпохой, SIGTERM без потери команд.

## Уточнение реализации (4a)
- **Подтверждение команд.** Вместо `XACK` по группе курсор потока (id последней применённой
  команды) хранится в снимке комнаты; записи удаляются `XDEL` и ответы отдаются только после
  успешного CAS снимка. Команды, не попавшие в снимок, новый владелец применит заново
  (идемпотентность — окно `op_id` в снимке).
- **Порядок записи итога.** Итог матча (`matches`, `match_players`, `match_rounds`, outbox)
  пишется после успешного CAS снимка закрытой комнаты; флаги `started_written` /
  `finished_written` в снимке делают повтор после handoff безопасным. Пока итог не записан,
  комната не отпускается.
