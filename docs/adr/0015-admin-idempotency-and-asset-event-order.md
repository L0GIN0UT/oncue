# 0015. Идемпотентность admin-мутаций и порядок событий ассетов

- **Статус:** принято (уточняет [0004](0004-outbox-and-idempotency.md) и [0012](0012-signed-asset-links-nginx.md))
- **Дата:** 2026-10-10

## Контекст
Ревью этапа 1 нашло три проблемы:

- Ключ `Idempotency-Key` резервировался в отдельной транзакции до мутации. Если мутация падала, ключ «залипал»: повтор получал отказ, хотя изменения не было.
- `version` в `AssetsReady`/`AssetsFailed` считалась по набору ассетов (`asset_set_id`). Новый набор той же единицы начинал счёт заново, и catalog не мог отличить устаревшее событие от свежего.
- Admin мог применить `UserRolesChanged`, который старше прав, уже полученных при входе. Тогда права в зеркале откатывались назад.

ADR 0004 описывает идемпотентность потребителей (inbox), но не HTTP-мутаций. ADR 0012 не описывает блокировку единицы и отказ Redis.

## Решение
**Admin-мутации** (identity, catalog, media_pipeline):

- `Idempotency-Key` обязателен на всех admin-мутациях: 8–128 символов `[A-Za-z0-9_.:-]`. Без ключа — 422 `idempotency.key_required`. Поле `reason` тоже обязательно, 3–500 символов. Общие зависимости — `gv_service.IdempotencyKey` и `gv_service.Reason`.
- Ключ `(actor_id, key)`, отпечаток запроса и ответ сохраняются в таблице `idempotency_keys` (`gv_db.idempotency.run_idempotent`) **в той же транзакции, что и мутация**:
  - откат мутации не оставляет ключа;
  - повтор с тем же телом получает сохранённый ответ;
  - повтор с другим телом — 409 `idempotency.key_reused`;
  - параллельный повтор — 409 `idempotency.in_progress`.
- Таблица аудита сервиса (`admin_actions` в catalog, `role_changes` в identity) хранит только аудит, ответов для повторов в ней нет.
- Права: `admin.access` и конкретное право действия (`require_perm`).

**Порядок событий ассетов:**

- `version` событий `AssetsReady`/`AssetsFailed` монотонна по `media_item_id` (= `aggregate_id`). Счётчик — `media_items_state.events_version`. Он увеличивается в транзакции записи события в outbox, поэтому в нумерации возможны пропуски.
- Потребители отбрасывают событие с `version` ≤ уже применённой. catalog хранит применённую версию на строке проекции `(media_item_id, clue_type, profile_key)`.

**Блокировка и выдача ссылок** (уточнение 0012):

- Блокировка единицы сразу удаляет объекты её ассетов из S3: уже выданные ссылки перестают работать раньше TTL.
- Разблокировка запускает новое поколение генерации.
- Если Redis недоступен при выдаче ссылки, лимитер работает fail-closed: 503 с `Retry-After`.

**Синхронизация прав в admin:**

- Ответ `admin-sessions` несёт `identity_version`.
- Admin не применяет `UserRolesChanged` с `version` ≤ сохранённой `identity_version`.

## Альтернативы
- **Резервировать ключ в отдельной транзакции до мутации.** Ключ залипает при сбое мутации (нашло ревью). Освобождать его по таймауту сложнее и всё равно оставляет окно.
- **Хранить ответы для повторов в `admin_actions`.** Смешивает аудит и механику повторов, плюс у каждого сервиса была бы своя реализация.
- **`version` по `asset_set_id`.** Не упорядочивает события разных наборов одной единицы.
- **Fail-open лимитера ссылок.** При отказе Redis выдача ссылок стала бы неограниченной. Цена 503 ниже: клиент повторит запрос.

## Последствия
- (+) Повторы admin-мутаций безопасны, и реализация одна для всех сервисов (`libs/db`, `libs/service`).
- (+) Проекции ассетов и права в зеркале admin не откатываются из-за событий, пришедших не по порядку.
- (−) Таблица `idempotency_keys` растёт. Периодическая очистка (`purge_older_than`) ещё не запущена — это хвост этапа 1 ([roadmap](../09-roadmap.md)).
- (−) Разблокировка единицы стоит полной перегенерации ассетов.
- Новый сервис с admin-мутациями подключает `gv_db.idempotency` и миграцию `idempotency_keys`.
