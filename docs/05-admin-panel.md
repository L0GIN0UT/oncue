# Админ-панель

> Статус: принято (v1). Решение: [ADR 0006](adr/0006-django-admin-panel.md).

## 1. Назначение

Внутренний инструмент для модерации, управления контентом, конфигами режимов и пользователями. Доступ — только у ролей `moderator` и `admin`.

## 2. Почему Django и как он вписывается в микросервисы

Django-admin даёт готовые списки, фильтры, поиск, формы, права и аудит. Писать это с нуля на React — недели работы без пользы для продукта.

Проблема: django-admin рассчитан на работу через ORM с **собственной** БД, а данные лежат в БД 13 сервисов. Прямая запись в чужие БД сломала бы инварианты доменов, outbox и события. Поэтому:

| Операция | Как делается |
|---|---|
| **Чтение (списки, поиск, карточки)** | Unmanaged-модели Django (`managed = False`) поверх **read-only реплик** БД сервисов (отдельный пользователь с правами только на SELECT). Отдельный database router на каждый сервис |
| **Изменение** | **Только** через `/admin/v1/...` API соответствующего сервиса. Кастомные actions и формы django-admin вызывают сервисный клиент. Сервис проверяет права, соблюдает инварианты и публикует события |
| **Собственные данные админки** | Своя БД: аудит-лог, сохранённые фильтры, заметки модераторов, назначения задач |

Сохранение формы через стандартный `save_model` для сервисных моделей запрещено: базовый класс `ServiceModelAdmin` переопределяет его на вызов admin-API, а модели помечены read-only.

## 3. Аутентификация и роли

- Вход через **identity** (OAuth2/OIDC-подобный поток). Своих паролей в админке нет. Django-пользователь — зеркало пользователя identity, создаётся при первом входе.
- Права Django (`is_staff`, groups, permissions) **синхронизируются из ролей и прав identity** при каждом входе и по событию `UserRolesChanged`.
- Обязательная 2FA (TOTP) для `admin`, рекомендуемая для `moderator`.
- Сессии админки короткие (8 ч), доступ только с allowlist IP или через VPN (настраивается).

| Роль | Доступ в админке |
|---|---|
| `admin` (суперпользователь) | Всё, включая роли, конфиги режимов, фича-флаги, биллинг, системные настройки |
| `moderator` | Очередь жалоб, комментарии, сборники, UGC-изображения, контент каталога (блокировка), санкции пользователям, просмотр матчей |
| `user` | Нет доступа |

Гранулярные права (`comments.delete_any`, `users.sanction` и т.д.) — см. [architecture/security.md](architecture/security.md) §2.

## 5. Аудит

- Каждое действие через admin-API пишется **в двух местах**: в аудит-лог админки (кто нажал) и в сервисе (что изменилось, с `actor_id` и `reason`).
- Для деструктивных действий обязательна причина (поле `reason`).
- Аудит-лог append-only, хранится не меньше 1 года.

## 6. Масштаб и отказоустойчивость

- Админка не на критическом пути пользователей. Её падение не влияет на игру.
- Чтение идёт с реплик, поэтому тяжёлые выборки не нагружают primary.
- Если сервис недоступен, его раздел показывает ошибку, остальные работают.

## 7. Структура

```
services/admin/
  src/admin_panel/
    core/            # ServiceModelAdmin, database routers, OIDC-бэкенд, синхронизация прав
    audit/           # своя модель аудита
    integrations/    # клиенты admin-API сервисов (генерируются из OpenAPI)
    apps/
      moderation/ users/ catalog/ collections/ game_config/ rating/ progression/ billing/ matches/
  tests/
```
